# クローゼットとコーデ提案を 1 画面にする (設計)

日付: 2026-11-05
状態: ドラフト (ユーザー承認待ち)

## 1. 背景と狙い

同僚にアプリを見せたところ「選択肢が多くてわかりづらい」「ボタンが隠れている」という評価だった。
具体的には、デモデータを取り込んだあとクローゼット画面で服を押したり「今日着た」を押したりして、
**そこから何かコーデが出てくると思っていた**。実際には「コーデ提案」タブ → 「条件を絞る」を開く →
「アイテムを選ぶ」ダイアログ、と 3 段階たどらないと「この服を着たい」が指定できない。

狙いは一つ。**服を押したら、その服入りのコーデがその場で出る**こと。
そのために「クローゼット」と「コーデ提案」のタブを無くし、1 画面にまとめる。編集は別画面に逃がす。

## 2. ゴール / 非ゴール / やってはいけないこと

**ゴール**

- メイン画面 1 枚で「条件を見る → 服を押す → 提案が変わる」が完結する。
- 日付・テイスト・気温 (予報) は常に見える。「条件を絞る」の折りたたみは無くす。
- クローゼットが 150 点あっても探せる (検索、カテゴリタブ、条件に合う服だけの絞り込み)。
- クローゼットが何点あってもメイン画面の縦の長さが暴れない (クローゼット領域は高さ固定)。
- スマホ (幅 600px 以下) でも同じ構成で使える。

**非ゴール**

- 提案ロジック (`src/lib/outfit.ts`) の変更。点数の付け方や多様性の仕組みは触らない。
- 編集画面 (今の `WardrobeView`) の機能追加・削減。追加 / 編集 / 削除 / インポート / エクスポート /
  ブランド絞り込み / 並び替え / 一品ごとの「今日着た」は今のまま。
- カバン対応、Supabase 連携などの別機能。

**やってはいけないこと (これをやったら失敗)**

- 服を押しても提案がすぐ変わらない、または別の操作 (決定ボタンなど) が要る。
- 主要な操作が折りたたみやダイアログの奥に隠れる。
- 150 点のクローゼットで提案が画面のはるか下に沈む。
- 既存の提案カード (人の絵 `OutfitFigure`、点数と内訳、「このコーデを着た」) の見た目や動きが変わる。

## 3. 決まったこと (ユーザーの決定)

ブラウザのモックアップ (案 A / B / C → C を 150 点向けに再検討した C1 / C2 / C3) を経て、
ユーザーは **C1「タブ 1 段 + グリッド」** を選んだ。決定事項:

1. メイン画面は上から **条件バー → クローゼット → コーデ提案** の順。
2. クローゼットはカテゴリをタブにして **1 段だけ** 見せる。中は横スクロールではなく **高さ固定のグリッド** で、その中をスクロールする。
3. 服を押すと即「着たい服」に入り、提案が再計算される。もう一度押すと外れる。
4. 検索欄と「今の条件に合う服だけ」フィルタ (既定でオン) で候補を減らす。
5. 服の並びは「最近着ていない順」。
6. 選んだ服はチップとして残り、タブを切り替えても消えない。
7. 下のコーデ提案は **今のカードのまま** (人の絵、点数、内訳バー、アイテム小カード、「このコーデを着た」)。
8. クローゼットの編集は **別画面**。一品ごとの「今日着た」ボタンはメイン画面には出さず、編集画面に残す。

## 4. 画面仕様

### 4.1 全体構成

```
┌ ヘッダー: Coordination / タグライン ─────────────────────────┐
│ (タブのナビは無くす)                                        │
├ 条件バー ───────────────────────────────────────────────────┤
│ 日付 [今日|明日|日付を指定] 2026/11/05   テイスト [指定なし|カジュアル|きれいめ|フォーマル] │
│ 東京 ▾ · 最高 15℃ / 最低 11℃ · 気温を変える · [秋] [冬の服も候補] [目安の厚さ: 4] │
│ (着用履歴があるときだけ) 最近着た服 [気にしない|控えめ|着ていない服を優先]          │
├ クローゼット (既定は折りたたみ: 1 行目だけ) ─────────────────┤
│ 着たい服: [● ボルドーニット ×] [● 黒ブーツ ×]  すべて外す  クローゼットを閉じる ▴  クローゼットを編集 › │
│ [🔍 名前・ブランド・タグで検索          ] [✓ 今の条件に合う服だけ]                 │
│ [アウター 9/20] [トップス 14/45] [ボトムス 11/30] [シューズ 12/20] [小物 35]     │
│ ┌───────────────── 高さ固定・内側スクロール ─────────────────┐ │
│ │ [■ ボルドーニット] [□ 白オックス] [□ マスタード] [□ ネイビー] … │ │
│ │  3 日前            未着用          12 日前       …         │ │
│ └──────────────────────────────────────────────────────────┘ │
├ コーデ提案 ─────────────────────────────────────────────────┤
│ #1 95 点 (人の絵 + アイテム + 内訳 + このコーデを着た)        │
│ #2 …                                                        │
│ [前の案に戻る] [別の案を見る]                                 │
└ フッター ─────────────────────────────────────────────────────┘
```

### 4.2 条件バー

今の `SuggestConditions` から「条件を絞る」の折りたたみを取り除き、中身を常時表示にする。

- 1 行目: 日付 (今日 / 明日 / 日付を指定 + date input) とテイスト。今のまま。
- 2 行目 (ステータス行, `data-testid="cond-status"` は維持): 地点 ▾、予報の気温、季節 pill、目安の厚さ pill。今のまま。
  - **気温の手入力** は「条件を絞る」の中にあった。ここに「気温を変える」リンクを置き、押すとその場に数値入力 (今の `temp-row`) が現れる。手入力中は「予報に戻す」ボタンも今のまま。**(私の判断: 折りたたみを無くしつつ、滅多に使わない入力欄で行を太らせないため)**
  - 予報の取得に失敗したとき (`forecast.status === 'error'`) と、この日付の予報が無いときは、数値入力を **最初から開いた状態** にする。エラー文言の「『条件を絞る』から気温を入力できます」は「気温を入力してください」に直す。
- 3 行目: 「最近着た服の扱い」のセグメント。着用履歴があるときだけ表示。今の `FRESHNESS_SEGMENTS` のまま。
- 「このアイテムを着たい」のボタンとチップ、`ItemPicker` ダイアログは **この部品から無くす**。役割はクローゼット領域に移る。
- `overrides` の件数表示 (「条件を絞る (2)」) は折りたたみと一緒に無くなる。

### 4.3 クローゼット領域 (新規部品 `ClosetPanel`)

**ヘッダー行**

- 左: 「着たい服:」に続けて選択中の服のチップ (色スウォッチ + 名前 + ×)。0 点なら「指定なし」(muted)。1 点以上なら「すべて外す」リンク。
  既存の `must-chip` / `must-remove` のクラスと `data-testid="must-chip"` をそのまま使う (既存テストが参照している)。
- 続けて「クローゼットから選ぶ」リンク (`aria-expanded`)。**既定は折りたたみ** で、検索・フィルタ・タブ・グリッドはこのリンクで開いたときだけ出す。
  開くと「クローゼットを閉じる」に変わる。開閉は `localStorage` (`coordination.closet.open`) に記憶し、次に開いたときも同じ状態にする。
  (2026-11-06 改訂、Issue #47。初画面にコーデ提案が 1 枚も見えなかったため。「着たい服」は任意の絞り込みで、提案が主役)
- 右: 「クローゼットを編集 ›」リンク。押すと編集画面へ (4.5)。

**検索とフィルタ行**

- 検索欄: placeholder「名前・ブランド・タグで検索」。既存の `filterWardrobe` を使う (名前・ブランド・タグの部分一致)。検索は **全カテゴリ** に効き、タブの件数にも反映される。
- 「今の条件に合う服だけ」トグル (チェックボックス風の pill、`aria-pressed`)。**既定でオン**。
  - 「合う」の定義: その服の `seasons` に、条件の `season` か `acceptableSeasons` のいずれかが含まれること。
    `src/lib/outfit.ts` の `seasonFit(item, conditions) > 0` と同じ判定。これを `fitsConditions(item, conditions): boolean` として export する (純粋関数、テスト対象)。
    **(私の判断: 厚さは入れない。厚さまで見ると「薄手ニットが冬に消える」ような取りこぼしが起きるが、季節だけなら「夏物が冬に出ない」程度で説明がつく)**
  - 選択済み (着たい服) の服は、フィルタや検索に合わなくてもチップには残り、提案にも使われる。グリッド上に見えなくなるだけ。

**カテゴリタブ**

- `ALL_CATEGORIES` の順で、**服が 1 点以上あるカテゴリだけ** 並べる。`role="tablist"` / `role="tab"` / `aria-selected`。
- ラベルは `CATEGORY_LABEL` と件数。フィルタか検索が効いている間は全タブを「トップス 14/45」の形にそろえ (減っていないタブも「1/1」)、どちらも効いていなければ「トップス 45」。(2026-11-06 改訂、Issue #52)
- 初期タブは、服のある最初のカテゴリ (通常はアウター)。タブの選択はコンポーネント内の state で、再マウントでリセットされてよい。
- スマホでは横スクロール (`overflow-x: auto`)、折り返さない (折り返すと 4 段になり提案を押し下げる)。右に続きがあるときだけ右端をフェードさせて、隠れたカテゴリがあると分かるようにする (2026-11-06 改訂、Issue #52)。

**グリッド**

- 現在のタブのカテゴリで、検索とフィルタに合う服だけを表示する。
- 並び: **最近着ていない順**。未着用 (記録なし) を先頭、次に最後に着た日が古い順、同点は **登録順 (配列順)** のまま (安定ソート)。
  今の `WardrobeView` の `sort === 'unworn'` と同じ規則なので、比較関数を共有してよい (編集画面の並びは変わらない)。
  着用記録を参照する日付は提案と同じ `dateStr` (`SuggestView` が持つ `wearStats`) を使う。
  **(私の判断: 名前順は入れない。履歴が無い新規ユーザーには登録順 = 取り込んだ JSON の順で並ぶ。編集画面と同じ並びにして驚きを減らす)**
- 検索でいまのタブが 0 件になり、他のカテゴリに該当があるときは、**該当のある最初のカテゴリ (`ALL_CATEGORIES` 順) のタブへ自動で移る**。
  検索語を消して戻しても元のタブには戻らない (移った先のまま)。フィルタのオン/オフでは自動で移らない。
  **(私の判断: この設計の狙いは「結果が隠れて見えない」を無くすこと。「ローファー」と打ってアウタータブの空表示だけ見せるのはその再発になる)**
- 高さ固定: PC で約 240px、スマホで 3 行分。中を縦スクロール。`max-height` と `overflow-y: auto`。
- 1 マス (タイル) の中身: 画像 (無ければ主色の面)、名前 (1 行で省略)、着用状況の短い文 (`describeLastWorn`、履歴があるときだけ)。
  `button` 要素で `aria-pressed`、`aria-label="<名前> を選択 / 選択解除"` (今の `picker-card` と同じ流儀)。選択中は枠を強調 + ✓。
- 押すと `mustInclude` をトグルする。親 (`SuggestView`) の既存の再計算 (150ms デバウンス、`stale` / `aria-busy`) がそのまま走る。
  同じ枠の服をすでに選んでいれば、その位置で **置き換える** (1 枠 1 点。`src/lib/selection.ts` の `toggleMustInclude`)。
  枠はカテゴリと同じだが、アウターだけは中間着 (`inferOuterLayer` が `mid`) と外套 (`shell`) を別の枠にし、
  提案ロジックが作る「中間着 + 外套」の重ね着を選べるままにする。
  (2026-11-06 改訂、Issue #49。同じ枠を 2 点押すと提案が 0 件になるのを、押す前に防ぐため)
- 0 件のとき (自動でタブを移しても全カテゴリ 0 件のとき): 「条件に合う服がありません。」。フィルタがオンで、オフにすれば出る服が全カテゴリ合わせて N 点あるなら「『今の条件に合う服だけ』を外すと N 点」のリンクを添える。このリンクはフィルタをオフにした上で、該当のある最初のカテゴリへタブを移す (チップでフィルタを切り替えただけのときは移らない)。

**クローゼットが空のとき**

- 条件バーとクローゼット領域は出すが、グリッドの代わりに今の `WardrobeView` の空状態と同じ案内を出す (折りたたみに関係なく出し、「クローゼットから選ぶ」は出さない):
  「まだアイテムがありません…」+ 「Gist / JSON から取り込む」(= `ImportDialog` をこの場で開く) + 「サンプルデータを読み込む」+ 「アイテムを追加」(= 編集画面へ)。
- コーデ提案の「先にクローゼットへアイテムを登録してください。」は、この案内と重複するので出さない。
- `ImportDialog` と「サンプルデータを読み込む」はクローゼットを書き換えるので、`SuggestView` に `onChangeWardrobe` と `onImportWearLog` (今 `WardrobeView` が受けているもの) を渡す。

### 4.4 コーデ提案

今のまま。`OutfitCard`、ページング (`PAGE_SIZE` 5、「別の案を見る」「前の案に戻る」)、「このコーデを着た」トースト、
空結果のメッセージ (着たい服を指定していて組めないとき / これ以上無いとき / トップス・ボトムスが無いとき) はすべて現状維持。

### 4.5 編集画面

- 今の `WardrobeView` をそのまま使う。先頭に「← コーデ提案に戻る」ボタンを加える (`onBack` prop)。
- App の state を `view: 'main' | 'edit'` にし、ヘッダーのタブは消す。URL ルーティングは入れない **(私の判断: 2 画面しかなく、戻る操作はボタンで足りる)**。
- 編集画面から戻ったとき、メイン画面の条件 (日付、テイスト、着たい服など) は **保たれる** こと。
  → `SuggestView` をアンマウントせず `hidden` で隠すか、条件 state を App に持ち上げるかは実装者に任せる。
  保たれないと「編集して戻ったら選び直し」になるので、必須要件として受け入れ条件に入れる。
- 編集画面で服を削除・置き換えしたとき、消えた id は `mustInclude` から外す (`SuggestView` が `wardrobe` の変化で刈り込む)。残すと `suggestOutfits` が全候補を捨てて提案が 0 件になる。チップにも出さない。

### 4.6 スマホ (幅 600px 以下)

- 条件バーは今の折り返しのまま。
- クローゼット: チップは折り返し、タブは横スクロール (右端フェード付き)、グリッドは 3 列で高さ 3 行分。
- 提案カードは今のまま。

### 5.2 テスト

TDD で進める。少なくとも次を書く (RED を確認してから実装)。

- `fitsConditions`: 当季の服は true、隣季 (`acceptableSeasons`) だけ含む服も true、まったく合わない服は false。
- 「最近着ていない順」: 未着用が先頭、次に古い順、同点は登録順 (配列順)。
- `ClosetPanel`:
  - タブは服のあるカテゴリだけ出て、件数が「14/45」形式になる (フィルタで減ったとき) / 「45」(減っていないとき)。
  - タイルを押すと `onToggle(id)` が呼ばれ、選択中は `aria-pressed=true`。
  - 検索で他カテゴリの件数も変わる。
  - 検索でいまのタブが 0 件になると、該当のある最初のカテゴリへタブが移る。全カテゴリ 0 件なら移らず「条件に合う服がありません。」。
  - 並びは未着用 → 古い順 → 登録順。
  - フィルタをオフにすると季節外の服も出る。
  - 選択中の服はフィルタで見えなくなってもチップに残る。
  - 空のクローゼットで案内と 3 つのボタンが出る。
- `SuggestView` (既存テストの書き換え):
  - 「条件を絞る」「アイテムを選ぶ」に依存するテストは、タイルを押す操作に書き換える。
    具体的には `SuggestView.test.tsx` の `openMore` ヘルパーと `アイテムを選ぶ` を使う 3 テスト、`SuggestView.ux.test.tsx` の 折りたたみ件数 `(1)` `(2)` と `アイテムを選ぶ` が無いことを確かめるテスト。
    「決定まで検索が走らない」(PR #42 のテスト) は **仕様が逆になる** (押した時点で再計算) ので、「押したら aria-busy が true になる」に書き換える。
  - タイルを押す → `must-chip` が 1 つ出て、提案が再計算される (`aria-busy`)。
  - 編集画面へ行って戻っても `mustInclude` と日付が保たれる (App レベルのテスト)。
  - `cond-status` の既存アサーション (地点名、手入力気温) は維持する。気温の手入力テストは「気温を変える」を押してから入力する形に直す。
- `ItemPicker.test.tsx` は削除。

### 5.4 受け入れ条件 (全部満たして完了)

1. タブのナビが無く、起動直後に条件バー・クローゼット (折りたたんだ「着たい服」の行)・提案が 1 画面に見える (クローゼットが空でも)。スマホ幅 (375×740) で提案の 1 枚目がスクロールなしで見え始める。
2. クローゼットのタイルを押すと、他に何も押さずに提案が再計算され、その服がチップと提案に現れる。もう一度押すと外れる。
3. 「今の条件に合う服だけ」が既定でオンで、タブの件数に反映される。オフにすると全件出る。
4. 検索欄で名前・ブランド・タグの部分一致で絞れ、全カテゴリの件数が変わる。
5. 150 点のクローゼット (テストで生成) でもクローゼット領域の高さが固定で、提案が直下にある。
6. 条件バーに折りたたみが無く、日付・テイスト・地点・予報・気温の手入力・(履歴あり時) 鮮度が全部その場で操作できる。
7. 「クローゼットを編集 ›」で編集画面へ行き、「← コーデ提案に戻る」で戻ると条件と着たい服が保たれている。
8. 編集画面の機能 (追加・編集・削除・インポート・エクスポート・ブランド絞り込み・並び替え・今日着た) は今のまま動く。
9. 提案カードの見た目と「このコーデを着た」は変わらない。
10. `npm test`、`npm run typecheck`、`npm run build` が通る。スマホ幅 (375px) で横スクロールが出ない。

5 と 10 の見た目の条件は jsdom では測れないので、テストではクラス名と DOM の順序を確かめ、実機 (Playwright MCP、375px と 1200px) のスクリーンショットで確認する。
